# Decision log

Decisions made where `PROMPT.md` leaves room, with the reason. Newest phase at the bottom.

## Phase 1 — Foundation

| # | Decision | Why |
|---|---|---|
| 1 | **Pinned dependency majors that still support Node 18**: `nodemailer@6`, `node-cron@3`, `rotating-file-stream@3`, `sanitize-html@2.17`, `pdfkit@0.17`, `pino@9`, `pino-http@10`, `otplib@12`, `ejs@3`. | The newest majors require Node 20–22 or are ESM-only (Node 18 cannot `require()` ESM). The brief requires Node 18, 20 and 22. A check of the production tree found no package needing Node > 18 and no install scripts (`npm ls --omit=dev`). |
| 2 | **Browser libraries are dev dependencies** (Alpine CSP build, Chart.js, KaTeX, highlight.js, Inter). `npm run vendor` copies them to `public/vendor` and the files are committed. | hPanel runs `npm install --omit=dev` and no build. KaTeX's CLI pulls in a Node-22-only `commander`; it is never needed at runtime. |
| 3 | **Alpine.js CSP build** (`@alpinejs/csp`) instead of the standard build. | The standard build needs `unsafe-eval`. The CSP build has its own expression parser, so `script-src` stays `'self'` + nonce + `js.paystack.co`. |
| 4 | **CSP allows `style-src-attr 'unsafe-inline'` only.** Style elements still require `'self'` or a nonce. | KaTeX output and Chart.js set inline `style=""` attributes on generated nodes. Script execution stays strict. |
| 5 | **Brand colours via `/theme.css`** (an RGB-triplet CSS-variable palette generated from Settings, cached by a hash of the colours). | No inline `<style>` is needed, the cache is immutable, and Tailwind classes such as `bg-primary-600` follow the brand without rebuilding CSS. Text colour on primary buttons is chosen for ≥ 4.5:1 contrast, and primary colours under 3:1 against white are rejected. |
| 6 | **Session store switches from memory to MySQL at install time.** | Before `/install` the database may have no tables, so the installer runs on a memory store. After the lock file is written, every session lives in the `sessions` table (created by the migrations with exactly the schema `express-mysql-session` expects). |
| 7 | **`auth_version` counter on users** for "sign out everywhere". It is incremented on password change or reset, suspension, role removal and 2FA reset. | Comparing `password_changed_at` failed for changes made within the same second, because MySQL `DATETIME` has second precision. A counter is exact. The current session is kept on a self-service password change. |
| 8 | **TOTP replay protection** (`users.totp_last_step`, updated conditionally). | A 6-digit code cannot be used twice, even inside its 30-second window or by two concurrent requests. |
| 9 | **Login lockout is stored in the DB** (`login_history`: 5 failures per email + IP in 15 minutes). There is also a per-IP `express-rate-limit` of 30 auth requests per 15 minutes. | It survives restarts, and the same table provides the per-user login history the security checklist requires. Unknown emails take the same time as wrong passwords (a dummy bcrypt compare). |
| 10 | **No privilege escalation**: an actor may assign a role only if they already hold all of its permissions. Only a Super Admin can grant Super Admin or edit a Super Admin, and the last active Super Admin cannot be demoted, suspended or deleted. | The brief says Admin "cannot change roles". This rule enforces that structurally, including for custom roles. |
| 11 | **Admin role** = every permission except `roles.manage`, `settings.manage`, `settings.payments`, `settings.payments.secret`, `audit.view`, `backups.manage`. | It matches the role table in §2: Settings, payment keys, roles and the audit log are Super Admin only. |
| 12 | **The permission catalogue lives in code** (`src/config/permissions.js`) and is synced to the DB on every boot. New permissions are granted to the built-in roles that include them by default. Admin edits are never revoked. | Later phases add permissions without a manual migration. |
| 13 | **`hpp` applies to query strings only.** | Forms legitimately post arrays (checkbox groups for roles and permissions). `hpp` on the body silently kept only the last value. Bodies are validated by zod instead. |
| 14 | **Multipart uploads carry the CSRF token in the query string** (`?_csrf=`); fetch calls use the `X-CSRF-Token` header. | The CSRF check runs before `multer` parses the body. |
| 15 | **Uploaded images are type-checked by magic bytes**, given random names, and stored under `storage/uploads/`. SVGs containing scripts or event handlers are rejected, and SVGs are served with a sandboxing CSP. | This is the upload hardening item of the security checklist. |
| 16 | **Deleting a user anonymises the row instead of removing it.** Email, name, phone, photo, 2FA and login history are cleared; `deleted_at` is set. | Orders, results and certificates reference the user. Certificates keep the holder name snapshot so a public verification stays truthful (documented for NDPR/GDPR). |
| 17 | **Email in development without SMTP** is written to `storage/mail-outbox/*.json` and logged. In production, a missing SMTP configuration makes the job fail visibly (Admin → Background jobs, plus a dashboard counter). | No silent loss of emails, and no fake "sent" state. |
| 18 | **Scheduler**: tasks record their last run in `settings` (`cron.last_run.*`). `node-cron` ticks every minute in-process. `/cron/run?token=` and `scripts/cron.js` call the same `runScheduled()`. | The in-process tick and the hPanel Cron Job never double-run a task, and jobs still run if hPanel idles the process. |
| 19 | **Timezones**: the DB connection uses `time_zone = '+00:00'` and every column is `DATETIME` holding UTC. Display uses the user's timezone, else the site's. Day and month boundaries for KPIs are computed in the site timezone (`utils/time.startOfDay/startOfMonth`). | This follows the brief. `DATETIME` avoids the 2038 limit of `TIMESTAMP`. |
| 20 | **JSON columns are read through `parseJson()`.** | MySQL 8 returns JSON as objects; MariaDB stores JSON as `LONGTEXT`. The app works on both. |
| 21 | **Bank transfer as a second payment method** (requested by the product owner). The schema is ready now: `orders.status = awaiting_transfer`, proof upload, review fields, and a dashboard counter. The flow ships in Phase 6. | Common in Nigeria next to Paystack. |
| 22 | **Google sign-in** uses a plain OAuth 2.0 / OIDC code flow with `fetch` (no Passport). It checks `state`, `iss`, `aud`, `exp` and `email_verified`. An existing account with the same verified email is linked. | Fewer dependencies. The ID token comes directly from Google's token endpoint over TLS (OIDC Core §3.1.3.7). |

## Phase 2 — Catalogue & question bank

| # | Decision | Why |
|---|---|---|
| 23 | **A single type registry** (`src/services/questions/types.js`) defines, for all 11 types, the authoring model, validation messages, conversion to and from stored rows, the candidate view and the content hash. | The editor, the importers (Phase 3), the grader (Phase 5) and exports all share one definition, so a type cannot behave differently in different places. The import dry-run will reuse the same human-readable messages. |
| 24 | **Versioning rule**: a version that has ever been live (`question_versions.published_at`) is immutable. Editing it creates version N+1 and repoints `current_version_id`. Versions that were never published are edited in place. The question type is locked after the first publish. | Past attempts keep the exact version they answered, as the brief requires, without creating a version for every draft keystroke. |
| 25 | **The authoring JSON is stored on each version** (`question_versions.authoring`) as well as the normalised option/answer rows. | Reopening the editor and exporting round-trip exactly, while grading and statistics read the normalised rows. |
| 26 | **Short texts use "inline markup"**: options, items, blank answers and labels are plain text with `` `code` `` and `\( maths \)`. Stems, explanations and rubrics are rich HTML, sanitised on save. | It keeps spreadsheet imports simple, prevents HTML injection in options, and still supports code and LaTeX. |
| 27 | **Author scope**: Question Authors can create and edit only their own **draft** questions, in assigned categories (sub-categories included). Published or in-review questions need `questions.edit_any` (Admin) or a reviewer to send them back. | It enforces the Draft → In Review → Published workflow. Admins assign categories on the user page. |
| 28 | **Reject requires a note.** Approving or publishing re-validates the question. A case study publishes or retires together with its child questions. | Reviews stay auditable, and broken questions can never go live. |
| 29 | **Duplicate detection**: sha256 of type + normalised stem text + sorted normalised option texts (and value/pairs for some types). It ignores formatting, letter case and option order. | It is the same hash the importer uses to flag duplicates (Skip / Overwrite / Import as new). |
| 30 | **Question images are private uploads** (`storage/uploads/private/questions`). They are served at `/qmedia/:uuid` to signed-in users only, type-checked by magic bytes, with dimensions read from the image headers (no native image library). | Exam content is not public, and the code stays free of native dependencies. |
| 31 | **The rich editor is a small `contenteditable` component** (bold/italic/lists, code, maths, tables, links, image upload and paste, HTML source view, "+ Blank") instead of a third-party editor. Output is sanitised server-side with an allow-list. | No large bundle, no `unsafe-eval`, and it works under the strict CSP. |
| 32 | **Alpine CSP build limits**: no template literals, no globals such as `String`, and no `x-html` in expressions. Helpers live in component methods, and HTML content is server-rendered (the ordering list moves real DOM nodes). | The build has its own expression parser. A browser test checks every page for Alpine and CSP errors. |
| 33 | **Training programme bands are keyed by name** in the form (`bands[Expert][…]`). | `qs` compacts sparse array indices, so index-keyed bands shifted whenever a middle band was left blank. |
| 34 | **Public catalogue pages are delivered with exams (Phase 4)**. Phase 2 provides the admin catalogue and the data model. | The public cards show exam duration, question count, price and attempts, which only exist once exams do. |

## Phase 3 — Import / export, AI generation, landing page

| # | Decision | Why |
|---|---|---|
| 35 | **One column spec** (`services/import/columns.js`) drives the parser, the templates and the xlsx export. Template examples are authoring models passed through the exporter. | Templates can never drift from what the parser accepts; a unit test re-imports every template and every export. |
| 36 | **Imports are two background jobs**: parse/validate, then import. Rows are stored in `import_rows` with messages, a decision and a result. The import job handles 100 rows per transaction (with a savepoint per row) and re-enqueues itself after about 15 s. | A 5,000-row file parses in about 14 s and imports in about 16 s without tying up an HTTP request or the cron call. One bad row never rolls back its batch. |
| 37 | **Undo** deletes questions the import created, unless candidates have already answered them, in which case they are retired. It restores overwritten questions to their previous version and status, and removes an exam the import created if it has no attempts. | Undo must never destroy evidence behind a result. |
| 38 | **AI output is an import source** (`imports.source = 'ai'`, `ai_generations` stores the prompt, model and token usage). | Generated questions get exactly the same validation, duplicate detection, human review and undo as uploaded files. Nothing AI-written reaches candidates unreviewed. |
| 39 | **Claude goes through the official `@anthropic-ai/sdk`** (pure JS, CommonJS, works on Node 18). It uses streaming (`stream().finalMessage()`) because outputs can be long, and structured outputs (`output_config.format` with a strict JSON schema). The default model is `claude-opus-5-5` at effort `high`, with server-side refusal fallbacks (`fallbacks: "default"`). Errors are mapped from the SDK's typed exceptions. **OpenAI** is called over REST with `response_format: json_schema` (strict). The model name is configurable, as is a base URL for Azure or compatible gateways. | It follows the platform guidance for each provider. Keys are encrypted at rest (AES-256-GCM) and never rendered. |
| 40 | **Generation is spread across certification domains by weight** (largest-remainder allocation), in batches of at most 20 questions per call. Each batch receives an avoid-list of stems already written, plus optional reference material. The system prompt requires original items (no brain-dumps), plausible distractors and teaching explanations. | Blueprint-faithful coverage, fewer near-duplicates, and grounded content. |
| 41 | **`organisation_id` added now** to questions, categories, imports and AI generations (NULL means platform content). | Company workspaces (Phase 7) need tenant-owned content; adding the column before data accumulates avoids a risky backfill later. |
| 42 | **Plans are products** (`type = 'plan'`, `audience = 'organisation'`) with `features` (marketing copy) and `limits` (enforceable quotas). | The landing page renders real plan records (no hard-coded pricing). Phase 6 adds Paystack subscriptions; Phase 7 enforces the limits. |
| 43 | **Cyber labs use a server-side simulated Linux engine** behind xterm.js and Socket.IO, with a pluggable `LabRunner` for an optional real-VM runner later. See `docs/ROADMAP.md` § 5A. | Hostinger cannot run containers, and a real shell on the web server would be unsafe. Server-side state means lab answers cannot be tampered with from the browser. |
| 44 | **The landing page uses only real data**: certification cards and question counts from the catalogue, and pricing from plan records. The hero illustration is HTML, not an image. | No placeholder or mock data in production paths; it is also fast, accessible and themable. |

## Phase 4 — Exam builder, instruction generator, SQL lab, AI exams

| # | Decision | Why |
|---|---|---|
| 45 | **Candidates are served from an immutable `exam_versions` snapshot.** Editing a live exam is allowed; the builder shows "unpublished changes" until it is published again as a new version. | Admins can fix a typo without taking the exam offline, and an attempt in progress never changes under the candidate. |
| 46 | **Settings that are not filtered or reported on live in `exams.settings` JSON** (delivery, integrity, scaling, instruction notes, certificate signatory), merged over typed defaults on read. Timing, attempts, scoring, price and release stay in columns. | Columns for what queries need; JSON for the long tail without a migration per toggle. |
| 47 | **Builder tabs autosave** 800 ms after the last change (JSON POST with field errors), and every tab still works as a plain form without JavaScript. Each save is audited with before/after values for the fields that tab owns. | Matches the brief's autosave requirement while keeping progressive enhancement. Saving one tab never overwrites another admin's tab. |
| 48 | **The instruction generator is a pure function of the exam summary** (`services/instructions`). It never reads the database or the clock. | Instructions can never contradict the settings, and it is fully unit-tested. |
| 49 | **Blueprint rules draw only published, top-level, non-case-study questions**, scoped to platform content plus the exam's own workspace. Availability is checked live while a rule is written and again before publishing. | Case studies are a group, not one item; drafts must never reach candidates. |
| 50 | **The pre-publish checklist has required and recommended items.** Required: content present and published, blueprint satisfiable, section timers ≤ duration, pass mark (or 0–100 bands for diagnostics), duration for timed types, price for paid exams, valid window. Recommended: category, short description. | Blocks broken exams without nagging about polish. |
| 51 | **SQL lab runs on SQLite compiled to WebAssembly (sql.js) inside a pool of worker threads**, on a fresh in-memory copy of the question's dataset for every run. Hard 3-second limit (the worker is terminated and replaced), 16 MB database ceiling, 200 rows shown, `ATTACH`/extensions blocked. | No native modules (hPanel), no access to the platform's MySQL, and a runaway query cannot affect other users. |
| 52 | **SQL answers are marked by comparing result sets with the model solution's**, not by comparing SQL text. Options: row order, column names, numeric tolerance. "Modify" tasks run the candidate's statements, then the author's check query. Feedback explains what differs (row/column counts, order) without revealing the expected values. | Any correct query scores, which is how real SQL skill is assessed. |
| 53 | **Every SQL question is executed before it is saved or imported** (dataset builds, the solution runs and returns rows). AI-generated SQL questions go through the same check and appear as errors in the preview if they fail. | A broken lab question must never reach a candidate. |
| 54 | **SQL dialect is SQLite** (standard SELECT, joins, GROUP BY/HAVING, subqueries, CTEs and window functions). Questions should avoid vendor-specific syntax; the editor says so. | One portable engine that runs anywhere Node runs. |
| 55 | **"Generate a complete exam" reuses the question generator and import preview**, then creates the exam on confirm. Duration and pass mark are scaled from the certification's official format (a scaled score such as 750 on 100–900 becomes 81.3% and turns on scaled reporting); the AI writes only the catalogue copy and an advice note. The exam is created as a draft. | The admin reviews every question, and exam rules come from facts rather than the model. |

## Phase 5 — Exam engine, grading, results, certificates

| # | Decision | Why |
|---|---|---|
| 56 | **An attempt is built from the latest published snapshot and records its exam version and every question version.** Fixed lists use the versions frozen at publish time; blueprint draws use the current published version of each drawn question. | Grading always uses exactly what the candidate saw, and later edits never change a result except through an explicit re-grade. |
| 57 | **`expires_at` is fixed at start** (duration × the candidate's extra-time accommodation, capped by the exam's closing time). Saves are accepted until `expires_at` + the exam's grace period + 5 s network allowance; a later save submits the attempt. A sweeper (every minute) submits abandoned attempts. | Server-authoritative timing: refreshing or switching device never resets the clock. |
| 58 | **Timed sections run in order.** Answers to items outside the current section are refused; an expired section moves on automatically; "Finish this section" moves on early. Linear exams refuse answers to earlier questions; per-question limits are enforced against the time the question was opened. | Section and question timers mean nothing if the server accepts late answers. |
| 59 | **Single-session exams use a per-attempt token** held in the candidate's session (and sent as a header by the player). Opening the attempt in another browser shows "Continue here", which issues a new token and locks out the old one. | Prevents two people sharing one attempt without blocking a candidate whose laptop died. |
| 60 | **Autosave is per item, debounced**, with an offline queue in `localStorage` replayed on reconnect and before submit; the header shows Saved / Saving / Offline. | Brief §3.6; nothing is lost on a dropped connection. |
| 61 | **Integrity events are recorded, never silently punished**: each tab switch, full-screen exit or copy attempt lowers an integrity score and appears on the admin timeline; auto-submit happens only when the exam sets a tab-switch limit with auto-submit. Reloading the page is not counted as leaving it. | Fair to candidates on unreliable devices, while giving examiners the evidence. |
| 62 | **Submit and grade run in one transaction, idempotently** (row lock on the attempt). The certificate is issued in the same transaction when the attempt passes; the email is queued afterwards. | Double clicks and sweeper races cannot create two results or two certificates. |
| 63 | **Essays (and SQL questions whose model solution fails) go to a grading queue**; the pass decision and band are deferred until every item is graded, then the certificate is issued and the candidate emailed. Manual grades survive re-grades. | Brief §3.7; a broken question must never cost a candidate marks. |
| 64 | **Result release**: full review / breakdown / score only are released at once; "after the window" is released by a scheduled task when the window closes; "manual" waits for an examiner (per attempt or all at once). Review, slip and explanations are hidden while withheld. | Protects the item bank and supports proctored sittings. |
| 65 | **Review shows option text without letters** (each candidate saw a different shuffled order), with ✔/✘ against their own choices. | Original letters would contradict what the candidate saw. |
| 66 | **"Practise my weak areas"** creates an untimed personal set (mode `study`) of up to 15 published questions from domains scored below 50%. It never counts as an attempt, never issues a certificate and is excluded from percentiles. | Brief §3.7 "Retake weak areas" without distorting exam statistics. |
| 67 | **Percentile** = share of other graded results on the same exam strictly below, plus half the ties. Shown as "—" until others have taken the exam. | Standard percentile-rank definition; stable with small groups. |
| 68 | **Certificates** use codes like `SSA-7KQ2-M9XD` (no ambiguous characters), a QR code to `/verify/<code>`, optional validity months, and can be revoked with a public reason. PDFs are drawn with pdfkit (no native modules) and cached in `storage/pdf`. Certificates for vendor-certification prep say they are not issued by the vendor. | Verifiable, honest, and hPanel-compatible. |
| 69 | **Paid exams require a live entitlement** (direct, via a bundle, or via the candidate's organisation). Checkout itself arrives with Phase 6. | Access rules are enforced now; selling is the next phase. |
| 70 | **The calculator evaluates expressions with a small parser**, not `eval`. | The CSP forbids `eval`, and it would be unsafe anyway. |

## Phase 6 — Commerce

| # | Decision | Why |
|---|---|---|
| 71 | **Paid exams create their own products** ("exam", and "attempts" when extra attempts are for sale) whenever the exam's price settings change or it is published, unpublished, archived or deleted. Bundles and company plans are managed under Products. | Admins set a price in one place; the shop cannot drift from the exam. |
| 72 | **One product per order** (attempt packs take a quantity). | Matches how candidates buy (one exam, one bundle, one plan) and keeps refunds and access exact. A cart can be added later without schema changes. |
| 73 | **Paystack without an SDK**: `transaction/initialize` → redirect → callback runs `transaction/verify`; the signed webhook (HMAC-SHA512 of the raw body with the secret key, constant-time compare) is the source of truth. Amount and currency are checked against the order. | Two HTTPS calls; no dependency to audit or update. |
| 74 | **Fulfilment is idempotent** (row lock on the order, `fulfilled_at`), so the callback, the webhook and an admin approval can arrive in any order and access is granted once. Every webhook delivery is logged in `webhook_events` with its outcome (processed, duplicate, ignored, rejected, error). | "A duplicate webhook doesn't double-grant; a tampered signature is rejected." |
| 75 | **Bank transfer**: the order shows the account details with the order number as narration; the candidate uploads a receipt (image/PDF, stored privately) and/or the transfer reference; an admin confirms (access + receipt email) or sends it back with a note. Unpaid transfer orders expire after a configurable time. | Many Nigerian buyers and companies pay by transfer. |
| 76 | **Coupons**: percentage or fixed, optional product list, minimum order, total and per-person limits, start/end dates. A 100% discount completes as a free order immediately. Redemptions are counted only when an order is paid. | Unpaid checkouts must not use up limited coupons. |
| 77 | **Company plans** create (or reuse) an organisation from the buyer's company name, make the buyer its manager, and record a subscription and an organisation entitlement for the billing period. With a Paystack plan code, renewals (`charge.success` on the plan) extend the period; `subscription.*` events update its status. Without one, companies renew by buying again. | Phase 7 workspaces read the active plan and its limits. |
| 78 | **Refunds remove access** (entitlements revoked, purchased attempts removed, subscription cancelled); the money itself is returned in Paystack or by transfer. | Paystack refunds are initiated in its dashboard; we keep access and records consistent. |
| 79 | **Admin grants** are ₦0 orders with method "admin" and a reason. | Scholarships and support fixes leave the same audit trail as purchases. |
| 80 | **Invoices and receipts are PDFs** with business name, address, TIN and the VAT portion (prices include VAT). They write "NGN" because the built-in PDF fonts have no ₦ glyph. | Companies need receipts for expense claims. |

## Phase 7 — Company workspaces

| # | Decision | Why |
|---|---|---|
| 81 | **A workspace is an organisation with an active company plan.** Its managers and authors use the normal admin screens (question bank, imports, AI generator, exam builder, attempts, grading) in *workspace mode*; managers also get the `/org` portal (people, cohorts, reports, settings). Members are candidates. | One set of screens to maintain; companies get the full builder, including SQL lab questions and AI. |
| 82 | **Isolation is enforced centrally**: in workspace mode only the content routes are reachable, and every `:id` in them is checked against the workspace before any controller runs (`router.param`). Lists and new content are scoped with `scopeOrg(req)`. A test walks the routes with another tenant's and platform ids and expects 404. | One place to get right, instead of a check in every handler. |
| 83 | **Platform staff never enter workspace mode**; the platform bank and exam lists show platform content only, while attempts and grading show everything (support). | Keeps the commercial bank separate from tenant content without blinding support. |
| 84 | **Workspace exams use only workspace questions**, are never public or paid (members only, an invite code — e.g. for job applicants — or a private link), and never appear in the catalogue. | Companies cannot repackage the paid platform bank; their content stays private. |
| 85 | **Plan limits are enforced where they bite**: candidates and staff seats when inviting (pending invitations count), published exams when publishing, AI questions per month when generating (from `ai_generations`). A lapsed plan keeps all data and the overview but closes the builder. | Clear upgrade moments without losing anyone's work. |
| 86 | **Joining is always by consent**: invitation links (bound to the invited email, 14-day expiry) or a join code the manager can rotate or turn off. | NDPR — nobody is added to an organisation silently. |
| 87 | **Cohorts** hold people and assignments (pre-training, post-training or general, with optional due dates). The progress grid uses each person's best released result; learning gain = post − pre for people who took both. Reminders go 48 hours before the due date, once. | Brief §3.10 learning-gain reports. |
